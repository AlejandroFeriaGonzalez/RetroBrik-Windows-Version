¿Qué es el Ecosistema BrickScript?
El ecosistema de BrickScript es una plataforma de prototipado rápido diseñada para facilitar el diseño, la experimentación y la evaluación de experiencias de juego mediante un Lenguaje de Dominio Específico (DSL). Este entorno permite que un diseñador defina las mecánicas, la estética y la interacción de un juego en un formato legible, transformándolo instantáneamente en un producto interactivo funcional para realizar pruebas de usuario.
Los componentes principales que permiten esta experimentación son:
Lenguaje de Definición (Archivos .brick): Es la herramienta de diseño donde se configuran los elementos de la interfaz, el tamaño del área de juego y, fundamentalmente, el mapeo de controles y la respuesta del sistema ante las acciones del usuario.
Compilador (compiler.py): Actúa como el motor de procesamiento que valida que las especificaciones de diseño sean coherentes antes de convertirlas en una experiencia jugable.
Representación Intermedia (Archivos .json): Un formato puente que organiza las decisiones de diseño de manera estructurada, permitiendo que el motor las interprete sin demoras.
Motor de Ejecución o Runtime (runtime.py): Es el entorno donde el diseño cobra vida. Se encarga de la retroalimentación visual (feedback), la gestión del flujo del juego y la visualización de la puntuación en tiempo real.
Interfaz Gráfica y Control: Utiliza la biblioteca Tkinter para ofrecer una representación visual estable y una gestión de eventos asíncrona, permitiendo que el usuario interactúe de forma fluida con el prototipo mediante el teclado.
Automatización (jugar.bat): Un script que agiliza el ciclo de iteración, permitiendo que el diseñador realice un cambio en el diseño y lo pruebe inmediatamente con un solo comando.
Este ecosistema está optimizado para ser extremadamente ligero y portable, permitiendo su ejecución en hardware limitado sin dependencias externas, lo que facilita su uso en sesiones de guerrilla testing o laboratorios de usabilidad básicos. Siendo capaz de funcionar en sistemas antiguos como Windows XP y caber en un disquete 1.44Mb, utilizando exclusivamente Python 2.7 sin necesidad de instalar librerías adicionales
Conceptos Fundamentales del Proyecto
Los siguientes términos son esenciales para comprender cómo el ecosistema permite iterar y evaluar la experiencia del usuario.
Lenguaje de Dominio Específico (DSL) como Herramienta de Diseño: Es un lenguaje especializado que permite al diseñador "hablar" directamente con el sistema de juego. En lugar de programar lógica compleja, el DSL de BrickScript permite configurar la usabilidad del juego, definiendo cómo se ven las piezas y cómo responden los controles a la intuición del jugador.
Compilador (Validador de Diseño): Actúa como el filtro que asegura que las decisiones de diseño sean coherentes. Su función técnica es traducir el código fuente, pero su valor en UX es garantizar que el prototipo esté listo para ser probado sin errores estructurales.
Gramática Formal (BNF) - El Manual de Estilo: Define los límites de lo que el diseñador puede crear. Es el "contrato" que asegura que todos los juegos mantengan una consistencia en su estructura, facilitando que el usuario aprenda a jugar rápidamente gracias a patrones familiares.
Entorno de Ejecución (Runtime) y Retroalimentación (Feedback): Es el motor donde ocurre la interacción. Desde la perspectiva de UX, el Runtime es responsable de la retroalimentación inmediata: gestionar que el dibujo en pantalla y el sistema de puntos respondan de forma gratificante a las acciones del usuario.
Representación Intermedia (Modelo de Datos): Es el archivo JSON que organiza las decisiones estéticas y lógicas. Para el diseñador, es una estructura transparente que permite auditar qué parámetros de diseño están afectando la experiencia final.
Diferencia entre Error de Sintaxis y Error de Experiencia (Lógica):
Error de Sintaxis: Un fallo estructural en el archivo .brick que impide que el prototipo inicie (ej. un paréntesis mal colocado). El sistema detiene la ejecución para evitar una experiencia rota.
Error de Experiencia (Lógica): El código es gramaticalmente correcto, pero la sensación de juego es deficiente. Por ejemplo, si una pieza cae demasiado rápido para la capacidad de reacción del usuario o si los colores elegidos confunden al jugador. Estos fallos se detectan mediante pruebas de usuario.
Iteración Rápida: La capacidad de modificar un valor en el .brick y ver el cambio inmediato, permitiendo fallar rápido y barato durante la etapa de diseño.
Affordance Visual: Cómo el diseño de las nuevas formas y colores en Tetris y Snake ayuda al usuario a entender intuitivamente qué objetos son beneficiosos o peligrosos.
Estado de Flujo (Flow): El ajuste de la velocidad y la dificultad para mantener al jugador motivado, evitando tanto el aburrimiento como la ansiedad.
Guerrilla Testing (Pruebas de Guerrilla): Es una técnica de evaluación de usabilidad rápida y de bajo costo que consiste en salir al entorno público para pedir a personas aleatorias que prueben el prototipo. En este proyecto, gracias a que el ecosistema es ligero y portable, los equipos pueden realizar estas pruebas de forma ágil, observando cómo un usuario desconocido interactúa con el juego de Snake o Tetris sin instrucciones previas.
A/B Testing (Pruebas A/B): Consiste en crear dos versiones de un mismo diseño (Versión A y Versión B) con una sola diferencia variable para comparar cuál ofrece mejores resultados. Los estudiantes pueden usar el archivo .brick para generar rápidamente dos variantes de un nivel (por ejemplo, una con colores fríos y otra con colores cálidos) y medir con qué versión los usuarios alcanzan una mayor puntuación o reportan menos fatiga visual.
Affordance Visual (Claridad de Uso): Se refiere a las características de un objeto que sugieren por sí mismas cómo debe ser usado. En BrickScript, el diseño de las nuevas formas y colores debe comunicar intuitivamente su función: una fruta roja brillante debería "gritar" que es un premio, mientras que una nube gris debería sugerir peligro o un obstáculo, permitiendo que el usuario aprenda las reglas del juego mediante la observación visual directa.
Estado de Flujo (Flow): Es el equilibrio psicológico donde el jugador está tan inmerso en la actividad que pierde la noción del tiempo. Los estudiantes deben ajustar variables como la velocidad de caída de las piezas en Tetris o el movimiento de la serpiente para evitar que el usuario caiga en el aburrimiento (si es muy fácil) o en la ansiedad (si es injustamente difícil).
Carga Cognitiva: Es la cantidad de esfuerzo mental que el usuario debe realizar para procesar la información en pantalla. Al diseñar niveles como "Nyan Cat" una serpiente multicolor, el equipo debe analizar si el exceso de colores y obstáculos satura la atención del jugador, provocando errores que no se deben a la falta de habilidad, sino a un diseño de interfaz confuso.
En este curso, los equipos no actúan como programadores de videojuegos, sino como Arquitectos de Experiencia. Un sistema de diseño es un organismo vivo que debe adaptarse a las necesidades del usuario final.
Evolución de la Interfaz: Originalmente, BrickScript ofrecía una interacción muy limitada. Para mejorar la satisfacción del usuario, el equipo debe intervenir el sistema para permitir elementos como el color, niveles de dificultad o "Power-Ups" que reduzcan la frustración del jugador.
Construcción de Primitivas de Diseño: Modificar el código de Python no es un fin en sí mismo, sino un medio para crear una infraestructura de prototipado más potente. Una vez que el sistema permite etiquetas de color o probabilidades, el diseñador puede iterar cientos de variaciones estéticas sin tocar el código base.
Ciclo de Iteración UX: El objetivo es experimentar el ciclo completo: desde definir una regla de interacción en la gramática, hasta observar cómo esa regla afecta la emoción del jugador en el Runtime. Al abrir la "caja negra" del proyecto, el lenguaje se convierte en un ecosistema adaptable a cualquier necesidad de diseño.
Meta Final: Consistencia y Retrocompatibilidad. Un diseño exitoso es aquel que evoluciona sin destruir el modelo mental previo del usuario. El sistema debe ser capaz de ejecutar las versiones más avanzadas sin perder la capacidad de ofrecer las experiencias clásicas y sencillas originales.
Descripción de los Archivos del Proyecto
Es fundamental comprender la función de los componentes que integran el ecosistema de BrickScript. A continuación, se detalla el contenido de cada archivo, estos archivos están en “RetroBrik Windows Version - Proyecto Base 2026-1s.zip” descargable del curso:
compiler.py: Este archivo constituye el núcleo del sistema de traducción, encargándose de transformar el código fuente escrito en lenguaje BrickScript en un formato estructurado de datos JSON mediante un analizador léxico y un parser de descenso recursivo.
runtime.py: Actúa como el motor de ejecución del juego y utiliza la biblioteca gráfica Tkinter para interpretar los archivos JSON generados, gestionando la lógica visual, el movimiento de los objetos y la detección de eventos en tiempo real.
jugar.bat: Es un script de automatización diseñado para sistemas Windows que simplifica el flujo de trabajo del usuario al coordinar la ejecución secuencial del compilador y el motor de juego con un solo comando.
README.txt: Proporciona la documentación esencial del proyecto, detallando los objetivos de BrickScript, las instrucciones de instalación y una guía rápida sobre la sintaxis necesaria para programar los juegos de ejemplo.
INSTALL.txt: Contiene los requisitos técnicos específicos para el despliegue del software, advirtiendo sobre la necesidad estricta de utilizar Python 2.7 y ofreciendo soluciones a errores comunes de configuración del sistema.
snake.brick: Representa un ejemplo práctico de código fuente que define la lógica, los colores y las reglas de interacción del juego de la serpiente utilizando la sintaxis específica del lenguaje BrickScript.
tetris.brick: Este archivo de ejemplo ilustra cómo definir formas complejas y rotaciones de piezas dentro del lenguaje, permitiendo a los estudiantes observar la implementación de la lógica clásica del juego Tetris.
snake.bnf: Establece la especificación formal de la gramática para el juego Snake, definiendo las reglas sintácticas que el compilador debe reconocer para validar las acciones y eventos permitidos dentro de ese contexto.
tetris.bnf: Define formalmente la estructura gramatical requerida para el juego de Tetris, sirviendo como mapa de referencia para entender cómo el lenguaje organiza las definiciones de piezas, cuadrículas y eventos de teclado.
snake.json / tetris.json: Estos archivos son el resultado del proceso de compilación y contienen una representación intermedia de los juegos en un formato que el motor de ejecución puede procesar de manera eficiente.

A. Requisitos Previos
Antes de comenzar, asegúrese de cumplir con las especificaciones técnicas del proyecto (ver archivo INSTALL.txt):
Intérprete de Python: Es obligatorio el uso de Python 2.7. Tenga en cuenta que el código no es compatible con Python 3 o versiones superiores.
Sistema Operativo: El sistema está diseñado principalmente para Windows XP o superior, aunque puede ejecutarse en otros entornos que soporten Python 2.7 y la librería Tkinter.
Dependencias: Aunque el proyecto solo utiliza módulos de la librería estándar de Python, los estudiantes deben realizar una verificación activa de las dependencias según su plataforma:
En Windows: Dependiendo de la versión de Python 2.7 instalada (por ejemplo, si se usó un instalador personalizado o minimalista), podría ser necesario reinstalar o activar el componente Tcl/Tk para que Tkinter funcione correctamente.
En Linux: Por lo general, Tkinter no se instala por defecto con el paquete base de Python. Es probable que el estudiante deba instalarlo manualmente mediante el gestor de paquetes (por ejemplo, sudo apt-get install python-tk).
Verificación: Se recomienda ejecutar el comando python -c "import Tkinter; print 'Tkinter listo'" en la terminal antes de iniciar el trabajo para confirmar la disponibilidad de la interfaz gráfica.
B. Instrucciones de Ejecución
Para ejecutar los juegos, siga estos pasos desde la consola de comandos (cmd.exe) (ver archivo README.txt):
Navegue hasta la carpeta raíz del proyecto, por ejemplo: cd C:\tpl.
Utilice el script de automatización jugar.bat seguido del nombre del juego.
Para probar Snake: escriba .\ jugar snake.
Luego Enter.
Para probar Tetris: escriba  .\jugar tetris
El sistema realizará automáticamente la compilación del archivo .brick a .json y, si no hay errores, iniciará el motor de juego (runtime.py) con la interfaz gráfica.

Tetris y la interrupción de memorias nocivas
Tetris y juegos similares han sido estudiados con sentidos terapéuticos, principalmente como “remedio” para síntomas de estrés postraumáticos, siendo útil al usar áreas del cerebro encargadas de gestionar la memoria visoespacial; mismos recursos usados a la hora de consolidar imágenes sensoriales traumáticas.
Fuente: Holmes, E. A., et al. (2009). "Can Playing the Computer Game ‘Tetris’ Reduce the Build-Up of Flashbacks for Trauma? A Quasi-Experimental Study of Distactor Tasks After Exposure to Traumatic Video Content”
Snake y la mejora motriz
Snake se basa en la planificación y la coordinación ojo-mano por ello se ha evaluado su uso en la mejora general de la coordinación motriz y más específicamente sobre pacientes con afectaciones neurológicas, recibiendo progreso en la corteza motora y prefrontal.
Fuente: Lumsden, J., et al. (2016). "Gamification of Cognitive Assessment and Cognitive Training: A Systematic Review"
      3. Efectos sobre el bienestar y la paciencia
Ambos juegos han demostrado ser eficaces para inducir el estado de Flow (fluidez), un estado psicológico donde el usuario está tan inmerso en la tarea que el sentido del tiempo y la autocrítica desaparecen. Esto es crucial en entornos hospitalarios o de alto estrés.
Fuente: Rodriguez, A., et al. (2021). "The Effects of Brief Play of Video Games on Stress Recovery"

Análisis Crítico de la Versión Original (Diseño "Base")
La versión inicial del ecosistema BrickScript y sus juegos de ejemplo (Tetris y Snake) es inherentemente excluyente, dado que su modelo de interacción es estrictamente visual. El motor de ejecución actual (runtime.py) asume que el usuario cuenta con habilidades cognitivas y físicas estándar, dependiendo exclusivamente de la capacidad para percibir cambios de color y posición en una cuadrícula. 
Sesgo del Espectador y Barrera de Interacción: El juego asume que el usuario tiene la agudeza visual suficiente para distinguir el rojo sobre un fondo negro en Snake. Al no haber texturas ni patrones, no existe una alternativa viable para usuarios con daltonismo o baja visión; las piezas se definen únicamente por su forma geométrica y un color sólido "quemado". 
Ausencia de Redundancia: El diseño base carece por completo de sonido, lo cual hace que la inmersión sea nula. Si un usuario no puede ver la posición exacta de una pieza, el sistema no ofrece estímulos que compensen esa pérdida de información, anulando la experiencia para personas invidentes o con visibilidad reducida. 
Carga Cognitiva y Ansiedad: En el caso de Tetris, la velocidad inamovible, la falta de un botón de pausa claro y los colores monótonos generan una alta carga mental, transformando el juego en una experiencia estresante y punitiva para perfiles con ansiedad (como nuestro usuario Andrés).
Propuesta de Adaptación: Hacia el Diseño Universal
Inspirados en el Manual de Diseño Inclusivo de Microsoft, nuestra versión no se limita a "añadir funciones", sino que reconoce los puntos de exclusión para mejorar la experiencia global. 
De la Exclusión a la Extensión (Tetris y Snake): Siguiendo el principio de "Resolver para uno, extender a muchos", propondremos el uso de patrones visuales y texturas dentro de los bloques. Si un usuario tiene dificultades para ver colores, la textura dentro del "brick" le permitirá jugar y tomar decisiones acertadas. Esto también ayuda a usuarios sin discapacidad visual que jueguen en pantallas con mucho reflejo. 
Uso Equitativo (Principio 1 del Diseño Universal): La adaptación propone mantener la misma lógica del juego para todos. En lugar de alterar drásticamente el código fuente, el sistema permite ajustar el tick (velocidad) o las paletas de colores en los archivos .brick según la capacidad de procesamiento sensorial del usuario, sin romper las reglas clásicas del juego. 
Adaptación de la Historia: El "Relato Espacial" y la "Arquitectura del Sosiego"
El diseño inclusivo nos obliga a replantear cómo se vive la experiencia para que sea significativa independientemente de los estímulos de los que dependa el usuario. 
Tetris (Arquitectura del Sosiego):
Para el público vidente: La historia se percibe como una coreografía visual de orden, donde la tensión se genera por la proximidad de las piezas al límite superior. 
Para el perfil ansioso: La narrativa deja de ser de "supervivencia" y se convierte en un refugio geométrico. Al suavizar los colores y reducir la velocidad tras un error, el ritmo del juego actúa como un regulador de la memoria de trabajo, ayudando a transitar de la alerta ansiosa a la calma. 
Snake (Relato Espacial):
Para el público con limitación visual: La historia se convierte en un mapa sonoro y táctil. Proponemos que la historia ya no trate de "sobrevivir en la cuadrícula", sino de "dominar el espacio a través del ritmo". 
Al incorporar una redundancia sensorial donde el entorno responde auditivamente a cada evento o pulsación de tecla, el ritmo se vuelve el lenguaje común. La emoción de la victoria puede ser compartida independientemente de si el usuario está viendo la pantalla o escuchando el mapeo del nivel.

Redundancia Visual y Alto Contraste
Actualmente, el motor dibuja bloques sólidos basados en un único color definido en el código. Para usuarios con baja visión o daltonismo, proponemos las siguientes mejoras: 
Patrones Internos (Texturizado): Se extenderá la gramática .bnf para incluir la etiqueta PATTERN_TYPE. En el motor (runtime.py), en lugar de usar rectángulos planos, se programará la lógica para dibujar una pequeña "marca" o patrón (ej. una cruz, un achurado o un punto central) en el centro de cada bloque. Esto permitirá distinguir las figuras del fondo y entre sí, incluso si el usuario no puede percibir el color. 
Paletas de Contraste Crítico: Se añadirá una validación en el compilador (compiler.py) que verifique y asegure una relación de contraste alta entre el color del objeto (ej. COLOR_SHAPE) y el fondo del canvas, siguiendo las pautas de accesibilidad web de la W3C. 
Simplificación y Diferenciación Geométrica
En el diseño original, tanto la serpiente como las piezas de Tetris son mayoritariamente rectangulares. La adaptación busca utilizar la geometría como un código de información: 
Identificación por Forma (Snake): Se modificará el script de Tkinter en runtime.py para utilizar el método create_oval al generar las piezas beneficiosas (como la comida). De este modo, un círculo representará un premio, mientras que el cuerpo de la serpiente y los muros seguirán utilizando create_rectangle, facilitando la distinción visual instantánea. 
Jerarquía de Tamaños: Para ayudar a la visión periférica, los obstáculos o los límites del nivel tendrán un grosor de borde mayor en su dibujado, destacándose del resto de los elementos en pantalla. 
Lógica de Señales Auditivas (Redundancia Sonora)
Para que el juego sea accesible a personas con visibilidad severamente limitada, introduciremos respuestas auditivas. Aunque el motor actual no gestiona audio, la lógica de implementación en Python 2.7 utilizará la librería estándar winsound (para Windows) o disparadores de eventos asíncronos: 
Sonificación de Posición o "Radar" (Snake): La lógica del runtime calculará la distancia entre la cabeza de la serpiente y la pared/comida. Emitirá un tono de frecuencia variable: una frecuencia alta indicará que el objeto o peligro está cerca, y una frecuencia baja indicará que hay espacio libre. 
Confirmación de Acción (Tetris y Snake): Cada vez que el motor detecte un evento en el teclado (ej. presionar las flechas direccionales), disparará un "click" sonoro muy breve. Esto confirma al usuario que el sistema recibió la orden de movimiento, reduciendo la incertidumbre y brindando soporte no visual. 
Sonificación de Altura (Tetris): (Propuesta adicional de la lógica) A medida que la pieza desciende en la cuadrícula, el motor emitirá un pitido rítmico cuyo tono se vuelve más grave conforme la pieza se acerca al límite inferior. Esto permite "escuchar" la posición vertical de la pieza sin mirar la pantalla.

Mapeo de Interacciones: De Teclado a Gestos Táctiles (Swipes y Taps)
La transición de teclas físicas a una pantalla táctil requiere aprovechar los gestos naturales del usuario para no sobrecargar cognitivamente la experiencia. 
Caso Tetris:
ON_KEY_LEFT / ON_KEY_RIGHT (Mover pieza): Se traduce a un Swipe horizontal (deslizamiento rápido hacia la izquierda o derecha). La longitud del swipe puede determinar si la pieza se mueve una o varias casillas. 
ON_KEY_UP (Rotar pieza): Se traduce a un Tap (toque rápido simple) en cualquier parte del área de control. El tap es el gesto más rápido, ideal para la urgencia de rotar la pieza antes de que caiga. 
ON_KEY_DOWN (Caída rápida): Se traduce a un Swipe hacia abajo (deslizamiento vertical descendente). 
Pausa / Menú: Se traduce a un botón virtual fijo y visible en una esquina superior, accionable mediante un tap.
Caso Snake:
ON_KEY_UP, DOWN, LEFT, RIGHT (Cambio de dirección): Se traducen directamente a Swipes direccionales (deslizamientos hacia arriba, abajo, izquierda y derecha). 
Alternativa de Accesibilidad: Para usuarios como Doña Martha (nuestra proto-persona), los swipes rápidos pueden generar fricción o imprecisión. Se puede ofrecer un modo opcional de "Pad direccional virtual" (D-Pad) fijo en la pantalla para tocar las flechas con el pulgar.
Gestión de la Obstrucción Visual (El problema del "Dedo gordo")
En entornos móviles, uno de los mayores retos de UX es que al interactuar, el usuario oculta información vital del juego con sus propios dedos o manos. 
Solución para Tetris:
División de la Interfaz (Split-Screen UI): Si el usuario toca directamente sobre el tablero de juego para hacer swipe, su mano tapará las piezas que están cayendo y el espacio donde deben encajar. 
Adaptación: La pantalla en orientación vertical (Portrait) se dividirá en dos zonas. El 70% superior será una zona de visualización pasiva (el lienzo o grid de Tetris). El 30% inferior será la "Zona de Gestos" (Gesture Pad). El usuario realizará todos los taps y swipes en esta área inferior, manteniendo el tablero de juego 100% libre de obstrucciones visuales en todo momento.
Solución para Snake:
Gestos Relativos Globales: En Snake, el jugador debe estar mirando constantemente a la cabeza de la serpiente y a la comida. Si intenta tocar la serpiente para guiarla, tapará su objetivo. 
Adaptación: El motor móvil registrará los swipes sin importar en qué parte de la pantalla se realicen (Trackeo relativo). El usuario puede mantener su pulgar descansando cómodamente en el borde inferior o lateral de la pantalla y hacer pequeños deslizamientos allí. Esto enviará la orden de dirección sin necesidad de que el dedo cruce el centro del lienzo, manteniendo la visibilidad total de la cuadrícula.

Anexo 4.C. Ejemplo. Justificación UX: Diseño Inclusivo y Adaptación Narrativa
1. Análisis Crítico de la Versión Original (Diseño "Base")
La versión inicial de BrickScript es inherentemente excluyente, ya que su modelo de interacción es estrictamente visual. El motor de ejecución actual (runtime.py) depende de la capacidad del usuario para percibir cambios de color y posición en una cuadrícula de 25 píxeles. Al no incluir sonido la inmersión es nula.
Sesgo del Espectador: El juego asume que el usuario tiene una agudeza visual suficiente para distinguir el rojo de la comida sobre el fondo negro en Snake.
Barrera de Interacción: No existe una alternativa para usuarios con daltonismo o baja visión, ya que las piezas se definen únicamente por su forma geométrica y un color sólido "quemado" en el código.
Falta de redundancia: Si un usuario no puede ver la posición de la pieza, el sistema no ofrece estímulos táctiles o auditivos que compensen esa pérdida de información, haciendo que la experiencia sea nula para el público invidente.
2. Propuesta de Adaptación: Hacia el Diseño Universal
Inspirados en el Manual de Diseño Inclusivo de Microsoft, la nueva versión no busca simplemente "añadir funciones", sino reconocer la exclusión y aprender de la diversidad para mejorar la experiencia de todos.
De la Exclusión a la Extensión: Siguiendo el principio de "Resolver para uno, extender a muchos", implementamos patrones visuales dentro de los bloques. Si un usuario tiene dificultades para ver colores, la textura o el patrón dentro del "brick" le permitirá jugar. Esto también beneficia a videntes que juegan en condiciones de alta luminosidad (reflejos en pantalla).
Uso Equitativo (Principio 1 de Diseño Universal): La adaptación propone que la lógica del juego sea idéntica para todos. En lugar de un "modo fácil", el sistema permite que el usuario ajuste el tick (velocidad) en el archivo .brick según su capacidad de procesamiento sensorial, sin cambiar las reglas del juego.
3. Adaptación de la Historia: El "Relato Espacial"
Para que la historia sea significativa para públicos invidentes y videntes, transformamos la narrativa de "colocar bloques" en una narrativa de orientación espacial.
Para el público vidente: La historia es una coreografía visual de orden y velocidad. La tensión se genera por la proximidad de las piezas al borde superior.
Para el público invidente/limitación visual: La historia se convierte en un mapa sonoro y táctil. Aunque el motor actual no emite sonido, la justificación propone que cada evento de la gramática (como ON_KEY_LEFT) genere una respuesta auditiva con "paneo" (estéreo). El sonido a la izquierda confirma el movimiento exitoso.
El "Pitch" unificado: La historia ya no es "sobrevivir en la cuadrícula", sino "dominar el espacio a través del ritmo". El ritmo (el tick del juego) es el lenguaje común que ambos públicos perciben, permitiendo que la emoción de la victoria sea compartida independientemente del canal sensorial principal.
4. Referencias y Marco Teórico
Microsoft Inclusive Design: Se aplicó el concepto de "Persona Spectrum" para entender que una mejora para un invidente (sonidos de posición) ayuda también a un vidente distraído o en un entorno ruidoso.
7 Principios del Diseño Universal:
Principio 2: Flexibilidad en el uso. El sistema permite diferentes métodos de interacción.
Principio 3: Uso simple e intuitivo. La reducción de la carga cognitiva mediante la eliminación de "ruido visual" en el grid.
Anexo 4.D. Ejemplo. Adaptación para Limitaciones Visuales: Estrategias de Redundancia Sensorial
Este análisis propone una evolución del motor de ejecución (runtime.py) y del lenguaje (.brick) para garantizar que la información crítica no dependa únicamente de la percepción cromática o la agudeza visual estándar.
1. Redundancia Visual y Alto Contraste
Actualmente, el motor dibuja bloques sólidos basados en un único color definido en el código o en el archivo .brick. Para usuarios con baja visión o daltonismo, se proponen las siguientes mejoras:
Paletas de Contraste Crítico: Implementar una validación en el compilador que asegure una relación de contraste mínima entre el color del objeto (COLOR_SHAPE) y el fondo del canvas (#000000), siguiendo las pautas de la W3C.
Patrones Internos (Texturizado): En lugar de rectángulos planos, se propone que el motor dibuje una pequeña "marca" o patrón (ej. una cruz o un punto central) en el centro de cada bloque para ayudar a distinguir la figura del fondo, incluso si el color no es perceptible.
2. Simplificación y Diferenciación Geométrica
En el diseño original, tanto la serpiente como las piezas de Tetris son mayoritariamente rectangulares. La propuesta de adaptación busca utilizar la geometría como un código de información:
Identificación por Forma: Se sugiere utilizar el método create_oval de Tkinter para piezas beneficiosas (comida o power-ups) y create_rectangle para obstáculos o segmentos del cuerpo.
Jerarquía de Tamaños: Las nubes obstáculo (en Snake) o el "Final Boss" (en Tanques) deben tener un grosor de borde mayor o un tamaño de bloque ligeramente superior para ser detectados mediante la visión periférica.
3. Lógica de Señales Auditivas (Propuesta Técnica)
Aunque el motor actual no gestiona audio nativo, se propone una lógica de implementación para Python 2.7 utilizando la librería estándar winsound o disparadores de eventos asíncronos:
Sonificación de Posición (Radar): La lógica debe emitir un tono de frecuencia variable según la proximidad de la cabeza de la serpiente a una pared o a la comida.
Frecuencia alta: Objeto cerca.
Frecuencia baja: Espacio libre.
Confirmación de Acción: Cada vez que el motor detecta un evento ON_KEY, debe disparar un "click" sonoro breve que confirme al usuario que el sistema recibió la orden de movimiento, reduciendo la incertidumbre sensorial.
